# Feature Discovery

使用这个 skill 调查已有能力的当前实际行为。围绕用户需要回答的问题组织探索，不按对象类型套用固定检查清单。

默认产物是对用户问题的证据化回答。只有用户明确要求写文档、沉淀文档、落地文档或生成文档时，才写入文件。

## 边界

- 将只读限制作用于探索阶段：探索期间不修改生产代码。
- 如果用户同时要求修复或实现，先完成现状与根因确认，明确探索结论，再退出探索阶段并进入正常实现工作流。
- 调查当前实际行为，不把设计目标、README、历史文档、注释或外部声明直接当作实现事实。
- 不把推断写成事实，不用缺失证据证明对象不存在。
- 不预设功能类型、技术形态、输出章节或领域检查项。

## Profile 路由

先判断是否需要加载项目专属 Profile：

- 当前仓库或用户明确涉及的仓库是 `drama-ios`、`famo-android`、`rn-starter-kit`；或
- 用户明确要求探索 Famo 多端功能。

满足任一条件时，完整读取并遵守 `references/famo-cross-platform.md`。否则不要读取该 Profile，也不要读取其中引用的文档模板。

Profile 只补充项目专属约束，不替代本文件中的调查契约、证据模型和停止条件。

## 项目约束

在调查和选择文档路径前，先阅读当前工作范围内适用的项目约束，例如：

- `AGENTS.md`
- README
- 既有文档规范
- 验证限制
- 文档输出目录和命名规则

将已有文档视为待验证的现状理解。最终结论仍需通过与问题相关的当前证据确认。

## 调查契约

开始搜索前，根据用户请求建立任务内调查契约：

- 调查对象
- 待回答问题
- 范围内
- 范围外
- 已知入口或锚点
- 需要的证据
- 预期产物
- 停止条件

优先从请求和仓库中自行确定这些内容。只有无法通过探索消除且会实质改变结果的歧义，才向用户确认。

调查契约用于控制探索，不要求逐项展示给用户。用户改变范围时，更新契约后再继续。

## 相关性门槛

在展开任何候选检查项前，先确认：

1. 它支持哪个待回答问题。
2. 什么证据可以确认、否定或限制相关结论。
3. 搜索到什么程度即可停止。

无法对应待回答问题的检查项直接跳过。不要因为某类证据在其他任务中有价值，就在当前任务中强制检查。

## 证据模型

分别记录证据来源与结论状态，不把来源类型当作可信度等级。

证据来源包括：

- 源码
- 配置
- 测试
- 运行观察
- 项目文档
- 外部声明

结论状态包括：

- **已确认**：当前范围内的直接证据支持结论。
- **有依据的推断**：多个证据共同支持，但缺少直接确认。
- **证据冲突**：相关证据不能同时支持同一结论。
- **未确认**：证据不足，或所需证据不在当前可访问范围内。

重要结论绑定具体证据，例如文件路径、符号、配置项、测试、日志或文档位置。引用外部声明时明确标注其来源性质。

报告“未发现”时，同时说明搜索过的范围、关键词或路径。将结论保持为“在已搜索范围内未发现证据”，不要写成“不存在”。

## 工作流

1. 阅读适用的项目约束，并按路由规则决定是否加载 Profile。
2. 建立调查契约，明确问题、范围、锚点、证据需求、产物和停止条件。
3. 从锚点定位实际入口，沿与待回答问题有关的控制流、数据流、状态变化或依赖关系追踪证据。
4. 对新增分支执行相关性门槛，只展开会改变或限定结论的路径。
5. 主动检查支持条件、反例、失败路径和证据冲突，但不扩展到契约范围外的系统盘点。
6. 为每个待回答问题确定结论状态，记录证据及其边界。
7. 所有问题均已确认、形成有依据的推断、标记冲突或明确未知后停止探索。

## 输出规则

只回复、不写文件时：

- 直接回答用户问题。
- 为重要结论附上证据。
- 说明影响结论的边界、冲突和未知项。
- 根据问题复杂度选择结构；窄问题保持简短，不强制完整梳理格式。

写文档时：

- 只在用户明确要求沉淀文档时写文件。
- 优先遵循当前仓库已存在的目录、命名、模板和作者规则。
- 如果无法发现适用规范且用户未指定位置，在写入前确认输出目录和文件名。
- 保留项目使用的内部链接、frontmatter、代码块和其他文档语法。
- 让文档结构服务于调查契约，不默认生成固定数量或固定类型的文档。

无论回复还是文档，都避免重复展开同一事实；完整表示证据可追溯，不表示穷举所有可能栏目。
