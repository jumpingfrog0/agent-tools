# Famo Cross-Platform Profile

仅在 `feature-discovery` 的 Profile 路由明确匹配时读取本文件。使用本 Profile 探索 Famo 已有业务功能在 `drama-ios`、`famo-android` 和 `rn-starter-kit` 中的当前行为、实现链路与差异。

本文件补充 Famo 专属规则；通用调查契约、相关性门槛、证据模型和停止条件继续以 `SKILL.md` 为准。

## 探索范围

1. 先从业务功能、用户路径或共享能力定义调查对象，不从某一端的类名推导完整范围。
2. 确定功能实际涉及哪些仓库，再分别定位入口和实现链路。
3. 对照与待回答问题相关的共享契约：
   - API 和数据模型
   - 路由及 RN Bridge
   - 配置、实验和 feature flag
   - 埋点名称与参数
   - 本地缓存和状态同步
   - 权限、生命周期、异常处理和降级路径
4. 将跨端差异区分为：
   - 产品定义上的合理差异
   - 平台技术差异
   - 疑似实现不一致
   - 证据不足，暂时无法判断

在某一端未搜索到实现，不等于该端不支持。继续检查 RN 实现、共享契约、服务端控制、灰度配置和跨端桥接；仍未找到时，记录搜索范围并标记为“未发现证据”。

## Famo 检查要求

围绕调查契约中的问题追踪：

- 用户路径和业务规则
- 状态变化、API 和数据流
- 持久化与缓存行为
- 错误、空态、加载、禁用、兜底和边界状态
- 参与链路的关键文件、符号和调用关系

对于用户侧业务功能，显式检查配置、实验、feature flag、服务端或本地开关、资源、文案和埋点。未发现时集中记录搜索范围，不在多个章节重复。

对于跨端功能，显式核对 API 模型、路由、Bridge、配置与埋点一致性。只展开与调查问题有关的差异，不做无关目录盘点。

## 文档信源

探索功能代码前，在 `.huangdonghong/docs/` 中搜索并阅读与功能名、模块名和入口名相关的现有业务及技术文档。

将已有文档视为待验证的现状理解，不作为最终事实来源。通过当前代码、配置、资源、文案、埋点、接口和数据流证据验证重要结论。

默认不要将以下目录作为当前功能事实来源：

- `.huangdonghong/feature`
- `.huangdonghong/report`
- `.huangdonghong/reports`

只有用户明确要求参考时才读取这些目录，并在输出中标注为参考材料。

## 文档目录与兼容契约

只有用户明确要求写文档、沉淀文档、落地文档或生成文档时，才生成两份正式文档：

```text
.huangdonghong/docs/<feature-slug>/<feature-name>业务梳理.md
.huangdonghong/docs/<feature-slug>/<feature-name>技术实现梳理.md
```

保持这个路径和文件名契约，以便 `ios-to-android-feature-migration` 消费最终文档。

- 从用户请求的功能名、业务名或模块能力名中提取功能标识。
- 跨模块能力使用能力名，不强行归入单个源码模块。
- `<feature-slug>` 使用稳定的小写短横线命名。
- 写入前在对话中明确最终目录和文件名。
- 同功能文档已经存在时，默认更新原文档，不新增重复文件。
- 作者优先沿用已有文档，其次遵循项目约束；没有可确认信息时省略作者，不要编造。

写文档前完整读取：

- `references/business-doc-template.md`
- `references/technical-implementation-template.md`

模板是检查清单，不要求逐章扩写。每份文档同时保留摘要和可追溯的完整归档；同一事实只在一个主要章节展开，“未发现”项集中归并。

## 回复结构

完整的 Famo 多端探索回复优先说明：

- 业务行为和规则
- 各端实现链路与差异
- 关键证据
- 已有文档缺口
- 影响结论的未知项

窄问题直接回答并附关键证据，不强制展开完整结构。
