# 工作流模型

## 文档所有权

需求根目录固定为 `.huangdonghong/feature/<feature-id>/`。

| 文件 | 唯一职责 | 创建时机 |
| --- | --- | --- |
| `需求.md` | 当前有效需求、待确认差量、未决事项、需求版本记录 | 启动 |
| `方案.md` | 当前有效方案、待审批差量、任务定义、方案版本记录 | 需求确认后进入技术评审 |
| `执行.md` | 唯一当前状态、阻塞、审批事件、任务进度和验收覆盖 | 启动 |
| `交付.md` | 实际修改、验证证据、偏差和遗留风险 | 进入交付阶段 |
| `.ui-design-cache.md` | 当前设计事实缓存 | UI Skill 按需生成并独立维护 |

不要生成独立审批单、checkpoint、决策日志、任务日志或 UI 测量文档。工作流不得读取 `.ui-design-cache.md` 正文；只消费 UI Skill 输出的审批级结论。

## 执行状态

`执行.md` 必须以以下 frontmatter 开头：

```yaml
---
workflow: drama-ios-feature-workflow-v2
workflow_version: 2
feature_id: <feature-id>
stage: requirement
status: draft
requirement_revision:
plan_revision:
active_tasks: []
---
```

阶段只允许：`requirement`、`plan`、`execution`、`delivery`。

状态只允许：`draft`、`blocked`、`awaiting_confirmation`、`awaiting_approval`、`active`、`completed`、`cancelled`。

版本标识只使用：

- `R1`、`R2`：已确认需求版本。
- `P1`、`P2`：已审批方案版本。
- `T-01`、`T-02`：实施任务。
- `AC-01`、`AC-02`：验收项；不是文档版本。

## 最小更新算法

每次准备写文件时依次执行：

1. 判定事实所有者，只选择一份正文文件。
2. 比较新旧内容；语义未变化则不写文件。
3. 修改最小的受影响章节或表格行。
4. 只在发生确认、审批、任务状态变化或阻塞处置时追加一条必要记录。
5. 不复制稳定内容，不因阶段变化重排或重写正文。
6. 写后检查未受影响文档保持字节不变。

需求和方案正文始终表示当前有效内容。版本记录只保存版本号、时间、动作和差量摘要，不保存每个版本的完整副本。

## 状态迁移

| 当前阶段 | 条件或口令 | 下一阶段与状态 |
| --- | --- | --- |
| requirement | 仍有未决事项 | `requirement / blocked` 或 `awaiting_confirmation` |
| requirement | `CONFIRM_REQUIREMENT` 且无阻塞 | 固化 `R*`，进入 `plan / draft` |
| plan | 方案尚未就绪 | `plan / draft` 或 `blocked` |
| plan | 方案可审批 | `plan / awaiting_approval` |
| plan | `APPROVE_PLAN` 且无阻塞 | 固化 `P*`，进入 `execution / active` |
| execution | 所有任务完成且验收有证据 | `delivery / active` |
| delivery | 交付门禁全部通过 | `delivery / completed` |

不得跳过中间门禁。取消需求时设置 `cancelled`，保留已有文档供审计，不删除文件。

## 变更口令

### REQUEST_CHANGES

先分类再落盘：

- 改变用户可见规则、失败行为、外部语义或 AC：进入需求待确认差量，阶段回到 `requirement`。
- 只改变实现、范围、任务、验证或 UI 实施结论：进入方案待审批差量，阶段为 `plan`。
- 只调整任务内部、不改变已审批方案：记录在对应任务偏差中继续执行。

只调整受影响任务和验收映射，不联动刷新所有文档。

### SKIP_BLOCKER

只在 `执行.md` 对应阻塞行记录替代方案、授权来源和处置结果。若替代方案改变需求或方案，继续走对应差量与门禁；口令本身不能替代确认或审批。
