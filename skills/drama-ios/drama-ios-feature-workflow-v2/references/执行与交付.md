# 执行与交付

## 执行阶段

恢复任务时先读取 `执行.md`，再读取当前 `R*` 的验收项、当前 `P*` 的相关章节和活动任务；不要默认重读所有文档。

默认一次只执行一个任务。只有用户明确授权并行，且任务修改范围与依赖不存在冲突时，才可同时激活多个任务。

### 单任务闭环

1. 读取任务目标、AC、允许范围、前置任务、实施约束和验证方式。
2. 确认当前代码仍满足方案前提；前提失效时先分类变更，不直接实施。
3. 仅在授权范围内修改代码、资源或工程文件。
4. 用 `git status`、`git diff` 和定向搜索核对实际范围；不得把用户已有改动计入本任务。
5. 执行仓库允许的静态验证，不主动构建、编译或查询 SDK。
6. 只更新 `执行.md` 中对应任务行及必要的验收覆盖行。

任务记录仅保留状态、实际修改范围、验证摘要和偏差；详细需求事实留在 `需求.md`，技术理由留在 `方案.md`。

### 执行期变化分类

- 任务内修正：不改变需求、方案或审批范围，在对应任务偏差中记录后继续。
- 方案变化：停止受影响任务，写入方案待审批差量，切换到 `plan / awaiting_approval`。
- 需求变化：停止受影响任务，写入需求待确认差量，切换到 `requirement / awaiting_confirmation`。
- 越界修改：立即停止，不自动扩大任务范围。

任务完成不得回写 `需求.md` 或已审批方案。若实际 diff 与方案不一致，先按上述分类处理。

## 交付阶段

只有所有任务完成且每个 `AC-*` 都有任务和验证证据时，才从 `assets/交付.md` 创建 `交付.md` 并进入 `delivery / active`。前置阶段不得维护空交付模板。

交付检查：

- 实际修改范围没有超出已审批边界。
- 每个 `AC-*` 都映射到已完成 `T-*` 和验证证据。
- 方案偏差已记录且未形成未审批变化。
- UI 任务包含视觉验证结论；无法执行的验证明确标为未验证并说明影响。
- `git diff --check` 通过，且没有把无关用户改动纳入交付。
- 所有阻塞项已关闭或通过有效 `SKIP_BLOCKER` 处置。

只按实际结果增量填写 `交付.md`。门禁通过后，将 `执行.md` 更新为 `delivery / completed`，清空 `active_tasks`，追加一条完成事件。存在无任务或无证据的验收项时不得完成交付。
