# 需求与方案

## 需求阶段

### 初始化

新需求只创建：

- `需求.md`：使用 `assets/需求.md`。
- `执行.md`：使用 `assets/执行.md`。

保留模板的稳定章节和标识规则，用实际内容替换占位符。此时不得创建空 `方案.md` 或 `交付.md`。

### 澄清与增量写入

- 把已成立的需求事实写入“当前有效需求”的对应章节。
- 把本轮新增但尚未确认的改变写入“本轮待确认差量”。
- 每个真实未知只在“未决事项”保留一条；不要复制到 `执行.md`。
- 每项可验证结果分配稳定 `AC-*`，后续不因排序变化重新编号。
- `执行.md` 只更新当前阶段、状态和阻塞摘要，不复制问题全文。
- 需求阶段只登记设计来源、用户规则和设计约束，不精读像素，不建立代码映射。

### CONFIRM_REQUIREMENT

仅当未决事项和需求阻塞均已关闭时接受口令：

1. 将待确认差量合入当前有效需求的对应章节。
2. 生成首个或下一个 `R*`，清空待确认差量。
3. 在 `需求.md` 版本记录追加一条差量摘要。
4. 在 `执行.md` 追加一条精简确认事件，更新 `requirement_revision`。
5. 切换到 `plan / draft`，从 `assets/方案.md` 创建 `方案.md`。

这些操作使用最小补丁；禁止借确认口令重新生成整个需求文档。

## 方案阶段

### 形成唯一方案

1. 读取当前 `R*`、相关项目上下文和当前代码事实。
2. 明确数据流、状态流、失败处理、修改范围与不修改范围。
3. 存在新 Objective-C 或 Swift 文件时，把工程文件注册纳入任务范围。
4. 将每个 `AC-*` 映射到一个或多个 `T-*` 和明确验证方式。
5. 有取舍或行为歧义时保持阻塞，不擅自形成多个并列方案让执行阶段选择。

图示只按复杂度生成：三个及以上参与组件使用组件图或数据流图；异步回调、通知或跨边界交互使用时序图；多状态、生命周期或并发治理使用状态图。简单局部改动不生成图。

### UI 需求

当前需求涉及 `design_images/` 时，按主 Skill 的固定参数调用 `$implement-ui-from-design-images`，并把当前 `R*`、设计约束和候选影响范围放入 `approval_boundary`。

工作流接收 fingerprint 和 cache 状态用于判断是否精读；cache 状态是单次调用的瞬时诊断值，不写入方案。`方案.md` 只维护以下稳定结论：

- fingerprint。
- UI 结构职责和组件决策。
- 资源方案、候选影响范围、视觉验证与门禁结论。

不得抄录缓存中的测量事实。缓存命中但代码映射改变时，只更新 UI 摘要、影响范围、相关任务和验收映射；审批级结论不变时不写任何工作流文档。图片、倍率或缓存 schema 变化导致刷新时，也只更新受影响章节。

### 任务定义

每个 `T-*` 必须包含：

- 目标。
- 覆盖的 `AC-*`。
- 允许修改范围。
- 前置任务。
- 实施约束。
- 验证方式。

任务应能独立判断完成，不得用“完成剩余工作”之类的开放描述。实际执行不得超出任务授权范围。

### 技术讨论与 APPROVE_PLAN

讨论期间只修改受影响的方案、范围、任务、风险或验证项，并将尚未审批的改变放入“本轮待审批差量”。

仅当方案唯一、阻塞关闭、AC 映射完整、任务范围明确、UI 门禁通过时接受 `APPROVE_PLAN`：

1. 将待审批差量合入当前有效方案。
2. 生成首个或下一个 `P*`，清空待审批差量。
3. 在 `方案.md` 版本记录追加一条差量摘要。
4. 在 `执行.md` 追加一条精简审批事件，更新 `plan_revision`。
5. 切换到 `execution / active`，把可执行任务写入任务看板。

禁止借审批口令重写整个方案文档或生成独立审批文件。
